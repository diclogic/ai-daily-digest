## Notable Papers & Research

### Google: agent teams produced machine-checked proofs at a scale no one has published before

A **Google Research** post dated **November 13** ("Advancing science & engineering with Antigravity's `/teamwork` feature") reports results from multi-agent runs built on Antigravity's `/teamwork` and **Gemini 4** models (sources name Argon; the exact lineup is not confirmable from here). The headline numbers:

- **Weil conjectures** — formalized in **Lean 4 at roughly 1.8 million lines**, produced across about **28,800 subagent invocations**. The underlying mathematics is Deligne's 1974 proof; the claim is about formalization, not new mathematics.
- **Courtade–Kumar conjecture (2013)** — reported as proved **in full generality** by a team from **Google, CUHK, USC and CMU** using a "Long Proof" pattern, formalized in Lean 4 at about **50 million lines**.
- **NMR structure determination** — **30 specialized agents** plus a physics-informed simulator in a self-correcting loop, reported at **95% top-1 exact match** on complex benchmark molecules, described as nearly double single-agent performance.
- **Software** — after profiling tools were added to the loop, a Rust rewrite of a C++ implementation ran **20–30% faster** on both x86_64 and ARM.
- **Access** — Google says `/teamwork` and `/boost` with Gemini 4 models are available to external users in Antigravity and Deep Review now, and it has **opened applications for 10,000 academic researchers** to get six months of free access to its highest usage tier.

**Architecture, as described:** each specialized agent receives only the files and tools its step needs, and independent critics and auditors review results without access to the original agent's reasoning — with **Lean 4 as the mechanical arbiter** of which work is correct.

*Why it matters:* this is the first credible claim that agent orchestration, rather than a single stronger model, is what unlocks proof-scale formal verification — and the Lean checker means the central claim is verifiable in principle rather than only self-reported. *Caveats that matter a lot here:* a Lean check establishes that the *formal statement* follows, not that the formal statement faithfully encodes the original conjecture — that match still requires human mathematicians, and outside review of 50 million lines has not happened. Google publishes **no cost figures** for runs using tens of thousands of subagent invocations. A separate GitHub repository (`dpwoodru/general-courtade-kumar-lean`, tied to [arXiv:2609.24931](https://arxiv.org/abs/2609.24931)) contains a Lean proof of the general Courtade–Kumar inequality described as **45,500 modules / 50.4 million lines**; the matching line count is suggestive but **the sources do not establish that it is the same work**, so do not treat it as corroboration. And **research.google was unreachable from this session** — none of this was read from the source post. ### Runway: Praxis-1 — a video foundation model repurposed as a robot controller

Runway's research report **"Praxis-1: From Video Pretraining to Robot Control"** is the technical case for calling the result a **world action model** rather than a vision-language-action model. The backbone is a **~26.9B-parameter mixture-of-experts diffusion transformer** derived from Runway's video foundation model, paired with a separate **314M-parameter action expert**. It takes camera images, a text instruction and robot proprioception, **predicts how the scene will change**, and derives matching actions from that prediction, re-planning continuously from new frames.

On **NVIDIA's RoboLab-120** leaderboard, the DROID-fine-tuned version scores **46.2% across 1,200 episodes**, against 42.9% for FLUX 3 Action, 36.8% for Cosmos3 Nano and 28.0% for π0.5 — the **top world action model and top open-source robot foundation model**, though **fifth overall** on the leaderboard. The most interesting finding in the writeup is diagnostic: Runway reports that **most residual errors come from wrong video predictions, not from the action module** — i.e. the bottleneck is world modeling, not control. *Caveats:* every figure is Runway-reported and **not independently replicated**; the base model needs an **80GB GPU**; and whether it genuinely needs less robot data than alternatives is still open. ([Runway research, not read](https://runway.com/research/praxis-1-video-pretraining-to-robot-control), [The Decoder](https://the-decoder.com/runways-open-source-praxis-1-turns-video-ai-into-a-robot-controller/), [FourWeekMBA](https://fourweekmba.com/ai-runway-open-sources-praxis-1-at-1-65x-pi0-5-on-nvidias-test/))

### Anthropic: a reference architecture for agents that wake up on their own

**"Building always-on agents"** (November 13, by **William Hu**) was **read directly today**. Its framing is the useful part: an always-on agent is *not* always on — it is idle most of the time and wakes for short **runs**, each of which processes one event, does the work and saves state. The architecture is five primitives:

- **Event inbox** — a durable store, an HTTP handler that acknowledges fast, and a single worker per inbox. The inbox is the source of truth, so a crashed worker's event can be retried; events are deduplicated by source ID and batched (several rapid user messages become one run). Deep checks such as **prompt-injection screening are deferred to the run**, not the handler.
- **Timers** — **follow-ups** (self-set deadlines) and **schedules** (recurring work), stored separately from the inbox; a poller moves due timers into it.
- **Memory** — durable storage, with the rule of thumb to **store only what the agent cannot look up again, otherwise store a pointer**. Types: user instructions, learned notes, past messages, per-task progress. An optional **"dreaming"** pass curates memory across sessions.
- **Permissions** — called out as **the area of greatest risk**, because runs carry the user's access unattended. Recommended pattern: an **external credential proxy** that injects secrets into outgoing requests so the agent never holds them, plus classifier review of risky actions, plus **deferred tool calls** that pause a run and ask the user (the answer returns as an inbox event).
- **Outbox** — users see outcomes, not streamed reasoning; the advice is to **start quiet and earn attention**, with evals tuning the noise/omission trade-off.

The cost claim driving the whole piece: on one long-horizon coding benchmark, **Opus 5.5 cost 78% less per solved task than Opus 5**, and about **40% less on typical workloads**. *Caveats, as stated in the article:* it is a pattern to adapt rather than a design; compaction and new sessions both lose detail; **auto mode does not replace user review** for consequential decisions; and the benchmark methodology is not given in the text. ([claude.com](https://claude.com/resources/articles/building-always-on-agents), read directly)

### Reserved slot: Cloudflare open-sources Kitesurf, a browser engine with no Chromium in it *(company not covered elsewhere in this digest)*

**Cloudflare open-sourced Kitesurf** under **Apache-2.0**, announced in its developer changelog dated **November 12** (most coverage says November 13). The repository was **read directly today**: it describes an experimental browser engine that **parses HTML, applies CSS, runs page JavaScript and renders screenshots without Chrome or a browser container**, stitching together **Blitz** (HTML/DOM/layout), **Stylo** (CSS), **Boa** (JavaScript, with a WebAssembly fallback) and Linebender libraries, plus **Krilla** for PDF output. It exposes a **Chrome DevTools Protocol endpoint**, so existing Puppeteer scripts connect without rewrites. One outlet reports roughly a **7× memory reduction** for typical agent tasks; that figure is Cloudflare's framing and not independently verified.

*Why it matters:* every agent browser shipped this year has been a Chromium container with a bill attached. If a Rust engine can serve the 80% of agent page-loads that do not need full browser fidelity, the unit economics of web-browsing agents change. *Caveats, from the README read directly:* the CDP endpoint is explicitly **"not a full Chrome implementation"**; it requires **Cloudflare Dynamic Workers, which need the Workers Paid plan**; the hosted DevTools frontend only connects to `127.0.0.1`, so it does not work against a deployed engine; and **the engine ships with no authentication of its own** — the README warns "Do not deploy Kitesurf without authentication in front of it," since a `workers.dev` URL is public by default and the deploying account pays for anyone's browsing. The **open-source release is the engine only, not the hosted Browser Run service**, and browser extensions are intentionally out of scope. ([repo](https://github.com/cloudflare/kitesurf), read directly; [Cloudflare changelog, not read](https://developers.cloudflare.com/changelog/post/2026-11-12-kitesurf-open-source/), [Phoronix](https://www.phoronix.com/news/Cloudflare-Kitesurf-Open-Source), [Linuxiac](https://linuxiac.com/cloudflare-open-sources-kitesurf-its-lightweight-browser-engine-for-ai-agents/), [Unite.AI](https://www.unite.ai/cloudflare-open-sources-kitesurf-browser-engine-for-ai-agents/))

**1. [cloudflare/kitesurf](https://github.com/cloudflare/kitesurf)** — *An experimental browser engine that runs on Cloudflare Workers.* Apache-2.0, **1.3k stars**, 60 forks, **375 commits**, 6 open issues, **34 open PRs**, Rust core with a JS/TS layer, topics `agents` and `browser-automation`. Full technical detail is in the launches section above. *Why it's trending:* it was open-sourced two days ago and is the first serious attempt to give agents a browser that is **not** a Chromium container — Blitz, Stylo and Boa assembled behind a Chrome DevTools Protocol endpoint, so Puppeteer code connects unchanged. *Caveats:* the CDP endpoint is **not full Chrome**; it needs **Cloudflare Dynamic Workers on the Workers Paid plan**; the hosted DevTools frontend only reaches `127.0.0.1`, so it will not attach to a deployed engine (the optional bundled frontend is a ~250MB download); `chrome://inspect` cannot reach an HTTPS engine; and it has **no authentication of its own** — the README's instruction is "Do not deploy Kitesurf without authentication in front of it," since `workers.dev` URLs are public and the deploying account pays for whatever anyone browses. Build needs Bazelisk, Node 22+ and pnpm 9.15.4, and the first Rust build is slow.

**2. [NVIDIA/SkillEvaluator](https://github.com/NVIDIA/SkillEvaluator)** — *Multi-tier framework for evaluating AI agent skills, with quality gates, semantic overlap detection, synthetic eval dataset generation and live agent evaluation.* Apache-2.0, **1.3k stars, +133 today** — the steepest single-day gain relative to base of anything on today's pages — 152 forks, **524 commits**, 13 open issues, 27 open PRs, Python (quickstart uses 3.13 via uv). Three independent tiers, each with its own CLI: **Tier 1 validation** (is the skill safe, well-formed, compatible with the harness), **Tier 2 deduplication** (embedding-based detection of guidance that repeats or overlaps, with an optional catalog for cross-skill comparison), **Tier 3 live evaluation** (runs agents with and without the skill in a Docker sandbox to measure whether it actually helps). A keyless deterministic `quality-check` scores a skill out of 100 — the bundled example gets **84.5 (B)** against a default pass threshold of **70** — and `rubric-eval` adds model-graded feedback. Ships CI integrations for GitHub and GitLab and installs as an agent skill via `npx skills add`. *Why it's trending:* the skills ecosystem has spent six months shipping thousands of skill packs with **no way to tell whether any of them improve agent behaviour**, and this is the first framework from a major vendor that measures the delta rather than reviewing the prose. It lands the same week Anthropic published its own argument that safety evals are saturated and gameable — the same problem one layer down. *Caveats, stated plainly in the README:* support level is **"Experimental,"** community-supported, **no SLA**; the keyless check covers **static quality only**, and publication evidence stays **INCOMPLETE** without scanners and live evaluation; a scanner that cannot run marks results INCOMPLETE and **exits nonzero**, and `--no-llm` does not remove that requirement; Tier 1 downloads pinned **SkillSpector and Gitleaks** releases when missing (Semgrep optional) — third-party software under its own licenses; Tier 3 autopilot generates only one skill-grounded case with limited coverage, so reviewing generated cases is advised; and model usage plus managed sandboxes **can incur charges**, with NVIDIA Build access subject to rate limits.

**3. [andrewyng/openworker](https://github.com/andrewyng/openworker)** — *An AI coworker for your everyday work, plus a Harness SDK for building agentic apps.* MIT, **19.2k stars, +100 today**, **2.7k forks**, **1,184 commits**, **208 open issues and 200 open PRs**, Python backend with a Rust SDK engine and a TypeScript/React desktop UI. Two things in one repo: a **local-first desktop app** that does research, document and spreadsheet creation, code and security review, scheduled tasks and Slack delegation; and **`@openworkerai/harness-sdk`**, which exposes the agent loop, tool calls, approvals and streaming for other people's apps. Models can be cloud (OpenAI, Anthropic, Gemini, OpenRouter) or local (Ollama, LM Studio, llama.cpp, vLLM), and it is built on Ng's own **aisuite**. *Why it's trending:* its governance defaults are the argument — **actions require approval by default**, tool calls are logged **with approval provenance**, and commands can run in an NVIDIA OpenShell or platform sandbox. That is the same permissions-first posture Anthropic's always-on agents article calls the area of greatest risk, shipped as a default rather than a recommendation, with the only cloud component being an OAuth-brokering service. *Caveats:* the desktop app is in **open beta**; **Windows builds are not code-signed**, so SmartScreen warns; macOS requires Apple Silicon and macOS 12+; sandboxing behaviour **varies by platform**; connectors need credentials; the maintainers say they **may not approve PRs** that add features already in development or that deviate from their vision — and **200 open PRs against 208 open issues** suggests that is biting.

**4. [elementalsouls/Claude-BugHunter](https://github.com/elementalsouls/Claude-BugHunter)** — *A skill bundle for Claude Code aimed at bug bounty hunting and external red-team work.* Code MIT, content CC BY 4.0, **5.9k stars, +124 today**, **901 forks**, **275 commits**, 3 open issues, 2 open PRs. Contains **82–83 skills** (the README and About text disagree), **15 slash commands**, and a dataset of **681 disclosed-report patterns across 24 vulnerability classes**, plus a `cbh` CLI and an engagement scaffolder. Per-class hunt skills cover XSS, SSRF, IDOR and SQLi; it also covers enterprise platform attack surface (M365/Entra, Okta, vCenter, SSL VPN appliances) and cloud IAM, with recon/OSINT, reporting and validation workflows. *Why it's trending:* the **901 forks against 5.9k stars** is the tell — people are adapting it, not bookmarking it — and the repo is unusually candid about the friction of doing authorized offensive work on a frontier model: it warns that **Anthropic's runtime cyber safeguards may block legitimate engagements**, points users to the Cyber Verification Program, and notes that on **Opus 5 some higher-risk requests may silently fall back to Opus 4.8**, which is easy to miss in a long session. *Scope and limits, as stated:* intended **only for assets you own or have written authorization to test** (in-scope bug bounty, pentest engagements, CTFs), with a validation gate that asks about scope before reporting; SECURITY.md **excludes** 0-day weaponization, post-exploitation tooling, malware development and mass targeting; and coverage is **external attack surface only** — internal AD attacks, C2 frameworks, persistence, evasion, iOS, binary exploitation and ICS are excluded by design. Roadmap items (a HackerOne MCP integration, more enterprise skills) are unfinished.

**5. [Tencent/LoopForge](https://github.com/Tencent/LoopForge)** — *Self-hosted workflows for coding-agent delivery.* MIT, **984 stars, +33 today**, **229 forks**, **324 commits**, 33 open issues, 35 open PRs, Go. The smallest repo in today's list and the only brand-new one from a major vendor. You describe a task to a **Main Bot** in chat; it opens a **Docker sandbox** with your repos, delegates to project roles, and can open a PR. **SOPs** are repeatable workflows mixing agent steps, script steps and **human approval gates**, and it orchestrates roughly **ten coding-agent CLIs** — CodeBuddy, Codex, Claude Code, OpenCode, Cursor CLI among them. **LoopForge Local** (`npx loopforge-cli`) runs the built-in workflows inside those assistants directly. Install is `git clone` then `./start.sh`, pulling a pinned GHCR image; needs Docker, Compose and Python 3. *Why it's trending:* it is the multi-agent-orchestrator pattern with the **approval gate made structural** rather than optional, from a vendor with its own coding agent to favour — and it does not favour it for execution. *Caveats, which the README states:* it is built **for trusted teams** — signed-in users can read project data across the instance, and **sign-up is open unless `AGENTFLOW_ALLOW_SIGNUP=false`** is set; sandboxes use the **host Docker socket**, explicitly "not untrusted multi-tenant isolation"; the default listen address is **`0.0.0.0:8090`** and the first account created becomes admin; model usage is **bring-your-own-key**; some features (requirement clarification, AI summaries) **only work with CodeBuddy models**, while Cursor CLI and Antigravity are not installed into SOP sandboxes and ZCode is not bundled; Local runs built-in workflows only, with SOP export "planned"; the **chat workbench is Chinese-only** for now; and GitLab/Gitea need separate SSH setup, with PR and issue automation requiring a hosting API token or a configured MCP.
