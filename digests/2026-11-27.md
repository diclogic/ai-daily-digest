# AI Daily Digest — November 27, 2026

**Top story: the Riemann artifact got both auditable and readable on the same day.** On **November 26** Waterloo number theorist **Michael Rubinstein** published the results of a full independent audit of the Alpöge–Claude Lean development — all **175,187 modules** recompiled, every module replayed through Lean's kernel, and the **1,484,729 declarations** the theorems depend on re-checked by **nanoda**, a second, independently written kernel — reporting that every check passed. Hours earlier, Anthropic researcher **Luke Sernau** released [`lsernau/grh-lean`](https://github.com/lsernau/grh-lean), which proves the same five theorems in about **76,000 lines instead of 17.37 million** — a roughly **228× compression** of the artifact that last week nobody could read. Separately, **OpenAI** posted a claimed **refutation of the polynomial Hirsch conjecture** with a Lean formalization, and **Anthropic disclosed that Claude rewrote its Messages API in Rust** for ~70% less CPU per request.

## Notable Papers & Research

### Anthropic shrinks the GRH Lean proof by ~228× — and it is 923 stars old

**Read firsthand.** [`lsernau/grh-lean`](https://github.com/lsernau/grh-lean) — *"A short Lean 4 proof of the Generalized Riemann Hypothesis"* — is **Apache-2.0, Copyright 2026 Anthropic, PBC**, with **923 stars, 102 forks, 10 watchers, 2 open issues and a single commit on `main`**. It ships **two editions of the same five theorems**: `grh/`, a **readable edition of about 300,000 lines** with its own `GUIDE.md`, and `grh-compact/`, **about 76,000 lines**. Each is a separate Lake project. Build requirements are **Lean v4.35.0 and Mathlib at commit `56a00585`**, with a stated build time of **one to two hours on 12 cores and 24 GB**, plus ~85 minutes if the Mathlib cache is cold. The README says the proof depends only on the three standard axioms — `propext`, `Classical.choice`, `Quot.sound` — verifiable by running `lake env lean scripts/PrintAxioms.lean`.

**The provenance, in the README's own words:** it is **"based on Levent Alpöge's, with Claude,"** linked to `alpo.ge/remark.pdf`, and is **"a shorter version, produced in collaboration with my colleagues at Anthropic, and Claude."** Note what it does *not* claim: it is not a new proof strategy, and the repository does not describe itself as an official Anthropic release.

**Why the number matters.** The original release was reported at **17,374,215 lines across 175,187 Lean 4 files** (covered in the Nov 21 and Nov 23 digests). The objection that dominated that coverage was not whether the code compiles but that **no human can read 17 million lines** — Brian Conrad's "frankly completely outrageous," Andrew Granville's call for a comprehensible write-up, and the reported **250,000-page** AI-generated expansion that was never released. A 76,000-line artifact, and especially a 300,000-line *readable* edition with a guide, is the first thing in this story that a determined mathematician could plausibly work through. That is a different kind of progress than another passing kernel check.

**The caveats are the README's own, and they are blunt:** the proof has **"passed machine checks only"**; **no mathematician has read it through**; **no paper accompanies it**; and the repository is explicitly a **"Research artifact. Not maintained and not accepting contributions."** ([officechai](https://officechai.com/ai/anthropic-researchers-use-claude-to-shrink-riemann-hypothesis-proof-from-17-4-million-lines-of-lean-to-76000/))

### The independent audit finished, and it is more thorough than anything reported so far

Dated **November 26**, Michael Rubinstein's verification page reports four distinct checks run on Waterloo compute servers with Claude Code, starting from Alpöge's published archive: a **full compile of all 175,187 modules**; an **axiom-dependency listing** for the theorems; a **replay of every module through Lean's own kernel**, which **accepted all 175,187**; and a check by **nanoda**, a second kernel written independently of Lean's, which typechecked the **1,484,729 declarations** the theorems depend on **with no errors**. He reports the same module counts as MIT's Andrew Sutherland, and reports that the ~76,000-line Sernau rewrite was checked as well.

**The part worth separating out.** Rubinstein also wrote a **human-readable working guide to the zeta-function case**, and its versioning is the most honest artifact in this entire story: **version 1 (164 pages)** takes a key inequality, **(M)**, from the Lean code **without proving it**; **version 2 (265 pages)** reduces (M) to **thirteen numbered hypotheses, none of them proved outright**. So after a week of certifications, the formal check is now about as complete as formal checks get, and the human explanation is still thirteen holes short. Those are two different questions and the coverage keeps merging them.

### OpenAI claims the polynomial Hirsch conjecture is false, with Lean attached

**Read firsthand.** The directory [`Superpolynomial-graph-diameter-of-simple-polytopes-November-24-2026`](https://github.com/openai/math/tree/main/preprints/Superpolynomial-graph-diameter-of-simple-polytopes-November-24-2026) in **openai/math** holds `paper.pdf`, a `build/` directory with LaTeX source, and a README. The claim: for every sufficiently large facet count *n*, there is a **bounded simple rational polytope** with *n* facets and **subpolynomial dimension** whose **graph diameter grows faster than any fixed power of *n***, which the README states **"disproves the polynomial Hirsch conjecture."** A strengthening is claimed too: two vertices can stay **superpolynomially far apart** even when each step is allowed to cross a face of dimension at most *s(n) = n^o(1)*.

**What is formalized and what is not.** The README links **Lean files** covering the refutation, the low-dimensional-face distance bound, superpolynomial vertex separation with a prescribed objective gap, and a quantitative lower bound with dimension and facet excess set independently — plus a **comparator challenge file** and a **formalization-scope document**. The paper is **authored as "OpenAI"** with no individual names and labelled a **"November 24, 2026 edition."** The README **does not say whether AI generated the paper or the formalization.**

**The companion is the bigger claim, and it is the one that is only half formalized.** The README links a separate OpenAI preprint on **strongly polynomial linear programming**, reported as claiming a resolution of **Smale's ninth problem** — a deterministic algorithm for explicitly given LPs with **arbitrary real coefficients**, returning an optimal primal–dual pair, an improving-ray certificate, or an infeasibility certificate. Per the scope note and third-party reads, **the Lean formalization covers only the fixed-rational case**; the **real-coefficient theorem is proved in the manuscript and is not formalized**. Neither paper is peer reviewed and no outside assessment has appeared. On Hacker News the Hirsch preprint drew **178 points / 49 comments**, with the thread largely arguing about whether the result is human, AI-assisted or AI-generated. ([mlq.ai](https://mlq.ai/news/openai-posts-unreviewed-proofs-claiming-answers-to-smales-ninth-problem-and-valiants-vp-vs-vnp-question/))

### Anthropic: Claude rewrote the Messages API in Rust, and the verification took five months

Announced **November 25**. Anthropic moved its **Messages API from Python to Rust**, reporting **~70% less CPU per request**, a **~20% reduction in median time to first token**, and (per several outlets) **>80% less memory**. Public traffic has run on the Rust service since **September 2026**, with **no downtime and no feature freeze**.

**The interesting number is not the 70%.** Reporting says **Claude wrote the Rust service in about a week** — one outlet puts Claude's share of the code at **over 80%** — and that **verifying it against live Python traffic ran until September**, using the Python service as a reference oracle with **autonomous Claude agents diagnosing discrepancies**. Output agreement reportedly climbed from **~24% to 99.6%** by August. That ratio — one week of writing, five months of checking — is the actual lesson for anyone planning an agent-driven migration.

**Caveats:** **TechRepublic reports the 70% figure describes Anthropic's broader development work rather than the Rust migration specifically**, and at least one analysis notes the post **does not separate gains from the language change versus the request-path restructuring**. No absolute or tail-latency figures were given. All numbers are Anthropic's own, and **the engineering post was not retrieved firsthand from this session.** ([TechRepublic](https://www.techrepublic.com/article/news-anthropic-claude-messages-api-rust-migration/), [BigGo](https://finance.biggo.com/news/f208d2d2-d751-4b23-9365-df00ba562057))

### Torvalds merges 41,000 lines of AI-assisted ext4 code, then tells its author to control the tooling

ext4 maintainer **Theodore Ts'o** sent a **94-commit** pull request on **November 24**, late in the **Linux 7.4-rc5** cycle; the merge adds roughly **41,200 lines across 68 files** (sources give 41,197 or 41,204 insertions). Ts'o said **most of the bug fixes were AI-generated** and **most of the new lines were KUnit tests written to validate AI-authored patches**. Torvalds **merged it anyway** and then objected in writing — the size and timing were wrong for an rc5, the tests belonged on a separate branch for the maintainers' own use, and he said he would **ignore the next pull that arrives this way**. The line being quoted everywhere: **"STOP THINKING THAT YOU — OR AI — NEVER ADD BUGS WHEN YOU FIX SOMETHING."**

**Why this is a bellwether and not a flame war.** Torvalds' objection is procedural, not ideological: coverage is consistent that he remains open to AI-assisted kernel work. What the thread actually demonstrates is a maintainer responding to AI-generated fixes by **generating tests to check them** — the same reference-oracle pattern Anthropic used for its Rust migration — and a release manager discovering that the bottleneck has moved from writing patches to **absorbing them on a schedule**. *The kernel mailing list thread was not read firsthand from this session.* ([Phoronix](https://www.phoronix.com/news/Linus-Torvalds-EXT4-AI-Big), [hwbusters](https://hwbusters.com/news/torvalds-merges-a-41000-line-ext4-fixes-pull-into-linux-7-4-rc5-then-tells-its-ai-helper-to-use-a-branch/))

**Today's four are a deliberate contrast: one proves a model can run with nothing underneath it, one gives an agent a real app's file formats, one gives it a game studio, and one gives it a policy engine.**

**1. [alesha-pro/llm.asm](https://github.com/alesha-pro/llm.asm)** — *three LLM projects in 17,252 lines of x86-64 assembly, with no C, no libc, no libm and no runtime.* **MIT**, **1.7k stars**, **250 forks**, **9 open issues / 9 open PRs**, **3 commits** (created after Nov 23). Assembled with `nasm`, linked with `ld`. Three phases: **`01-qwen3-inference`**, a **14,712-byte** static ELF running **Qwen3-0.6B (Q8_0)** with a built-in BPE tokenizer, GQA, QK-Norm, RoPE and SwiGLU, with a `--chat` REPL and KV-cache; **`02-baremetal-os`**, a **24,252-byte** bootable OS running the same model with **no Linux or Windows underneath** (Multiboot 1 → long mode → AVX2/FMA/F16C → ACPI/APIC SMP, with VGA, PS/2 and COM1 I/O); and **`03-minigpt-train`**, a **32,944-byte** FP32 Mini-GPT trainer with a hand-written **6×16 AVX2+FMA SGEMM**, full analytical backward pass, decoupled AdamW and a live 80×24 Braille TUI.

**Why it's trending, and why the numbers are worth your attention:** it hit **228 points / 57 comments** on HN as "Bare Metal Qwen," but it is not a stunt — it reports beating **llama.cpp** on decode at every thread count on an **EPYC 7642**: **20.70 vs 16.63 tok/s** at 1 thread (+24.5%), **103.64 vs 80.79** at 8 (+28.3%), peaking at **126.81 tok/s** at 40 threads (+19.8%), with the bare-metal OS build faster still (**134.9 tok/s**, booting in **74–94 ms**). Numerical parity is reported as **cosine 0.99965 with 64/64 exact greedy tokens** against PyTorch FP32 on the fast path and **1.000000000** against the Python Q8_0 reference with `FAST_Q8=0`; training reports **27,662 tokens/s** and **gradient cosine 1.0000000000 across all 21 tensors** versus PyTorch CPU. **Caveats, and the author states most of them:** **the llama.cpp comparison is decode-only and not apples-to-apples** — llama.cpp batches GEMM for prefill while llm.asm prefills token by token; **the fast path is not bit-exact**; benchmarks come from **essentially one machine type**; the About blurb's "12 KB / 22 KB / 32 KB" **disagrees with the README's own byte counts**; the Phase 3 TUI shows `best_val=1.8399` while the summary claims **val_loss 1.51**, suggesting different runs; Phase 2 is verified on **QEMU/KVM and one Proxmox Xeon**, not broadly on real hardware; and Phase 3 is a **character-level Mini-GPT on TinyShakespeare**, not a serious training stack. Requires **AVX2/FMA/F16C** (Haswell/Excavator or newer).

**2. [obsidianmd/obsidian-skills](https://github.com/obsidianmd/obsidian-skills)** — *the Obsidian team teaching agents its own file formats.* **MIT**, **54.1k stars** (**+704 this week**), **3.8k forks**, **111 commits**, **3 open issues / 2 open PRs**. Seven skills on the **Agent Skills** specification: **obsidian-markdown** (Obsidian Flavored Markdown — wikilinks, embeds, callouts, properties), **obsidian-bases** (`.base` files with views, filters, formulas, summaries), **json-canvas** (`.canvas` nodes, edges, groups), **obsidian-cli** (vault access plus plugin and theme development), **obsidian-headless** (sync and publish from the command line with no desktop app), **defuddle** (clean Markdown extraction from web pages, explicitly to cut token use) and **knap** (render Markdown templates from JSON or CSV, with batch generation).

**Why it's here:** this is a **first-party vendor shipping agent skills for its own open formats** — installable across **Claude, ChatGPT/Codex, Antigravity, Cursor, Copilot, Grok Bot, Hermes, Kiro, Muse, OpenCode and Gemini CLI** — rather than a third party reverse-engineering them. Against a trending board dominated by generic "skills" bundles, the thing being standardized here is **the data format, not the prompt**, and `defuddle` existing purely to reduce context cost is a tell that this was written by people who actually run agents. **Caveats:** **Muse runs in Meta's cloud, so `obsidian-cli` does not work there** and using Obsidian Headless under Muse means **signing in and syncing your vault into Meta's cloud**; **Gemini CLI installs only from a tagged release** and silently falls back to a manifest-less source archive if extra files are attached; manual installs require copying folders to per-agent paths the README **does not fully specify**; several install paths depend on **marketplaces the repo does not control**; and the README lists **no prerequisites for the CLI/headless skills, no supported Obsidian versions and no tested agent versions**.

**3. [nexu-io/opengame](https://github.com/nexu-io/opengame)** — *a game-development pipeline wrapped around whatever coding agent you already run.* **Apache-2.0**, **1.3k stars**, **219 forks**, **123 commits**, **11 PRs listed** (created after Nov 23). A browser-based **Game Studio**, **25 playable templates** as editable HTML5/JS and Three.js source, and an **MCP server exposing 12 `openmotion_game_*` tools**. The pipeline is the interesting part: generated games run a **QA loop** of static validation → **50-tick smoke test** → headless balance simulation → **headless Chromium playtesting** → cover capture → trailer rendering, with pass thresholds of **<5 ms per tick** and **<2,500 ticks** per simulation. Distribution goes to a local catalog, a web share link, or a **9:16 playable-ad mode**. Model is **BYOA + BYOK** — bring your own local agent (Claude Code, Codex, DeepSeek, Gemini CLI and others) and your own keys.

**Why it's here:** almost every agent-plus-games project stops at generation. This one treats **automated playtesting as the deliverable** — a headless browser actually plays the output and a tick budget gates it — which is the only part of the category that generalizes. **Caveats, and there are many:** the About section advertises **"100+ viral games"** while the README documents **25 templates**, and agent support is **"20+" in one place and 22 in another**; "AAA-grade 3D" and "monetization-ready" are **unevidenced marketing**; the README references a model name this session could not verify; several badges push a **paid OpenDesign Go subscription with a Black Friday discount**; platform publishing (WeChat, Douyin, TikTok, itch.io), top-100 templates and the live model arena are **roadmap, not shipped**; **Git LFS is required** and templates download assets on first use, with **only one template working offline**; multiplayer beyond room-based playtesting is **not described**; and **no performance benchmarks are reported at all** — the tick numbers are pass criteria, not measurements.

**4. [w01fb0ss/PiBot](https://github.com/w01fb0ss/PiBot)** — *a local-first desktop app where named bots work in folders you choose, under one policy engine.* **Apache-2.0**, **660 stars**, **93 forks**, **171 commits**, **5 open issues**, five contributors. Built on the **pi agent kernel**. Each **Bot** has a name, a role (developer, researcher, …), its own model, skills, permissions and memory; in **group chats** a coordinator plans the work, assigns steps and gathers results, **with the plan confirmed by you before it runs**. Bots are confined to **working folders you select**, changes are listed for review, and on macOS they can be **restored from automatic checkpoints**. Runs on macOS/Windows/Linux with an **Android** companion, an optional self-hostable relay, runners on other machines, and ACP access from editors. Models via **Ollama**, OpenRouter, your own keys or certain subscription sign-ins. Architecture is clean enough to be worth copying: the **brain does not depend on Electron**, so it runs headless, and **`packages/agent` is the only place the kernel is used**, pinned as an npm dependency.

**Why it's here:** the design rule is that **a single policy engine governs every tool call** — commands run sandboxed, and approvals, commands and outbound sends are all logged — rather than safety being a prompt instruction. The privacy claim is unusually specific too: **no telemetry**, PiBot's own servers never receive chats or files, and a privacy document enumerates every outbound connection. **Caveats:** **checkpoint restore is macOS-only**; mobile is **Android-only**; phone/runner/relay features involve opt-in outbound connections; and the README is honest that **whichever model provider you choose still sees every prompt** — local-first is not local. It also **says nothing about performance, model quality or project maturity**, and building from source needs **pnpm 12** and a separate `PIBOT_DATA_DIR`.

**Also worth a look:** **[lsernau/grh-lean](https://github.com/lsernau/grh-lean)** (**923 stars**, 102 forks, 1 commit, **Apache-2.0**, created after Nov 20) — the Anthropic GRH compression covered at the top of this digest is also, mechanically, one of the fastest-rising new repositories on GitHub this week, and the only **Lean** project anywhere near the board. Worth cloning for one reason even if you never read a line of the maths: it is a working example of **shipping a formal artifact with a guide, an axiom-printing script, two editions at different readability/size tradeoffs, and a README that states plainly that no human has checked it**.
