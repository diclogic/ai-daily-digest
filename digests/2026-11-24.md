## Notable Papers & Research

### Google DeepMind: AI agents that write quantum programs a theorem prover will accept

**"Discovering formally verified quantum programs with AI"** — Google DeepMind and Google Quantum AI, [arXiv:2611.09822](https://arxiv.org/abs/2611.09822). The team built a **Lean 4 library grounded in quantum Hoare logic with classical variables**, then had **Gemini 4** agent teams propose candidate quantum programs that are machine-checked against formal specifications for both **correctness and resource cost**. Reported improvements over the published baselines: **~2.55×** in parallel search, **~290×** in quantum arithmetic, and roughly **11×, 8× and 2.5×** on fusion, photochemistry and drug-metabolism simulation respectively.

**Why it matters:** this is the same template as the Riemann-in-Lean story that dominated this digest last week, applied to a domain where nobody can check the work by running it — the target circuits exceed any existing quantum computer. Formal verification substitutes for the experiment that cannot be done. The Lean library and the discovered programs are **public** at [google-deepmind/formal-quantum-computation](https://github.com/google-deepmind/formal-quantum-computation) (discoveries on a separate branch), which is what makes the claim auditable.

*Caveats, and they matter:* every speedup is an **estimated resource cost from analysis, not a measurement on hardware**; nothing here ran on a quantum computer. The paper itself first went up **November 6** and was revised through mid-November — the **November 23** date is the *announcement*, not the preprint. Secondary coverage also disagrees on the figures (11× vs 11.8×, 2.55× vs 2.57×, ">290×" vs "~290×"), so treat the exact multipliers as approximate. Sources: [The New Stack](https://thenewstack.io/deepmind-lean-quantum-verification/), [Quantum Computing Report](https://quantumcomputingreport.com/google-deepmind-and-google-quantum-ai-use-lean-4-to-discover-formally-verified-quantum-algorithms/).

### CoEvoBench: can a model improve both the model *and* the harness?

**"CoEvoBench: Can LLMs Drive Recursive Co-Evolution of Agentic Systems?"** — Chuan Xiao, Baojie Wang, Haizhao Fan, Hongzhe Du, Xander Xu (Alibaba Group, with Zhejiang University and Shanghai Jiao Tong University), [arXiv:2611.27116](https://arxiv.org/abs/2611.27116), submitted **November 20**, listed **November 23**. The benchmark puts an LLM in the **researcher** seat: starting from a shared **9B base model** and a starting harness, it gets a **24-hour budget** to train, revise, or both, across five agentic domains, then submits a model-harness pair scored on held-out tasks. The point is the part prior benchmarks skipped — earlier work either froze the harness or froze the weights, leaving **the choice of which to change** unmeasured.

**The result is the interesting part.** The strongest of five frontier researchers closed **more than four fifths** of the gap to an instruction-tuned reference system, but co-evolution worked on interaction tasks and **rarely on long-horizon coding**, and the authors' conclusion is pointed: current models can make a strong *first* improvement but **cannot yet use feedback from the system they just improved to make the next one.** That is a direct, measured answer to the recursive-self-improvement question that has been argued rhetorically all month. Code: [AlibabaResearch/CoEvoBench](https://github.com/AlibabaResearch/CoEvoBench). *Caveat:* self-reported headline numbers, not peer reviewed; author-to-affiliation mapping is read off the PDF layout.

### Who grades the agent?

**"Who Grades the Agent? Privilege Separation for Coding-Agent Benchmarks"** — Nathan Nour Houlamy, Mattia Favretto, Earlence Fernandes, Mauro Conti, [arXiv:2611.27860](https://arxiv.org/abs/2611.27860) (cs.CR, cs.AI). Coding-agent benchmarks normally grade by **executing the agent's own code**, which means the thing being measured controls the measuring apparatus. **SplitBench** splits running the tests from judging the results: a **trusted grader holds the expected answers**, so an agent that fully controls the test environment — and can read all the grading code — still cannot forge a pass. The threat model names **rewriting a test's outcome** as its own attack class. A secondary write-up reports SplitBench agreeing with native graders on **98.7%** of agent attempts; that figure is from the [DEV write-up](https://dev.to/aahyouoos/can-you-trust-a-coding-agents-benchmark-score-4d00), not verified against the paper here.

### Briefly

- **CodeReviewBench** ([arXiv:2611.26942](https://arxiv.org/abs/2611.26942)) grades AI code review by **what developers actually do**: a bot suggestion acted on counts as useful, one ignored does not. The authors cross-check against a 50-PR offline benchmark and report the two agree on precision rankings. Honest limitation, stated by the authors: it **does not provide a reward signal**, so using it for RL would need a learned proxy.
- **Illumina's BioInsight AI Lab released CellularAI** (**November 19**), an open-source algorithm for predicting transcriptome-wide responses to genetic perturbations **in cell types it has not seen** ([illumina.com](https://www.illumina.com/science/genomics-research/articles/introducing-the-cellularai-algorithm--predicting-single-cell-res.html)). Illumina frames it explicitly as a window into active research, **not a finished result** — unusually restrained for this category.

## Model & Product Launches

### GLM-5.4: the first flagship that runs its layers twice

**Z.ai (Zhipu) shipped GLM-5.4 on November 23**, its **first Loop Transformer flagship** — and the most-discussed model release of the window (**1,083 points / 351 comments** on Hacker News). In a standard transformer each layer runs once per forward pass; GLM-5.4 runs the **28 layers of the GLM-5 base twice**. At roughly **750B parameters**, Z.ai claims it reaches the capability level of **2–3T-parameter** models, and says it validated the loop structure at **1B, 4B, 30B and 750B** scales before committing it to a flagship. It promises to keep scaling loop depth and model size together, with a much larger model "coming soon."

**Why it matters:** this is a real architectural bet against the parameter-count trend — buy capability with *depth reuse* rather than more weights, which changes the memory-versus-compute tradeoff at serving time. **The caveat is severe, though:** the launch post contains **not a single benchmark score** for GLM-5.4 itself. There is **no API** (listed as coming after a safety evaluation), **no download** (open weights promised after safety hardening), and access is limited to **GLM Coding Plan subscribers** via ZCode and Z.ai Chat. A 2–3T-class claim with zero published numbers and no way for anyone to check it is a press release, not a result. ([TNW](https://thenextweb.com/news/zai-glm-5-4-loop-transformer-coding-model), [TestingCatalog](https://www.testingcatalog.com/z-ai-launches-glm-5-4-its-first-loop-transformer-model/), [i10x](https://i10x.ai/news/glm-5-4-zai-loop-transformer-coding-plan))

### Ant open-sources a 560B medical MoE under MIT

**LingSante-3.1-flash** — Ant Group's Ant Ling team, released around **November 22** and widely covered **November 24**: **560B total parameters, ~25B active per token**, **MIT licensed**, on Hugging Face under the **inclusionAI** org, alongside **LingSante-3.1-air-VL**, a **124B multimodal** model (5.5B active). The family is being released in phases. Ant claims it outperforms **GPT-6 Astra, Claude Opus 5.5 and Gemini 4 Argon** on three benchmarks.

**Why it matters:** an MIT-licensed 560B model aimed at medicine is a meaningfully different offer from a restricted-access frontier model, and the license is the part that will have consequences. **Three caveats to carry:** every benchmark row is **Ant's own internal testing**, with no independent replication at release; the model card advertises **1M-token context** while the **shipped config caps at 262,144** — a discrepancy that exists in the repo and is absent from Ant's public materials; and the documentation states plainly that it **is not a medical device**. ### Reserved slot: AWS Strands Decider v2 — five open models that pick instead of write *(a company not covered elsewhere in this digest)*

**AWS released Strands Decider v2 on November 23**: **five open-weight decision models built on Google's Gemma 4**, from **2B to 31B** (E2B, E4B, 12B, 26B-A4B, 31B), all **Apache 2.0**, weights on Hugging Face and code in the open Strands Decider repo. These models do not generate text. Given a state — a support ticket, say — plus a question, they **return a probability over a fixed set of options**. AWS reports the largest scoring **71.5** on the public **Decision Index 0.3** benchmark versus **48.8** for the largest v1 model.

**Why it earns the slot:** almost every agent failure that matters is a **routing** failure, not a prose failure, and a calibrated 2B classifier is the right-sized tool for a decision that hinges on one detail — far cheaper and more auditable than asking a frontier model to think out loud. **Caveats:** the benchmark figures are **AWS's own**; the models are **not yet on Amazon Bedrock**; and at least one write-up notes **Google's own Gemini Decision 1 still has the lowest calibration error**, which is the metric that actually matters for a model whose entire job is outputting a probability. ([VentureBeat](https://venturebeat.com/data/awss-strands-decider-v2-targets-the-agent-decisions-that-hinge-on-a-single-detail), [Techmeme](https://www.techmeme.com/261123/p55), [Unite.AI](https://www.unite.ai/aws-releases-strands-decider-v2-and-sandboxes-more-coding-agents/))

### OpenAI and Cisco ship Shirudo: agent-written eBPF shields for unpatched Linux

Launched **November 23** ([openai.com](https://openai.com/index/introducing-shirudo/), [Cisco newsroom](https://newsroom.cisco.com/c/r/newsroom/en/us/a/y2026/m11/cisco-and-openai-launch-shirudo-a-new-project-to-safeguard-agentic-ai.html)), **Shirudo** uses **eBPF** to block a specific exploit on a **running** Linux server while a real patch is built and deployed — closing the window between disclosure and rollout. The shields are **generated by agents**: in Cisco's demo, a shield written with **Codex blocked a Java4Shell exploit against Elasticsearch without restarting the service**. Licensing is **BSD 2-Clause** (BPF programs dual BSD/GPL), with roots in Cisco's **Tetragon**, "rewritten for the agentic era."

**Why it matters:** this is agent-generated code being inserted into the **kernel path of production servers**, which is about as high-trust a placement as exists — and the pitch is that the alternative (an unpatched box) is worse. **Status caveats are load-bearing:** the GitHub repo lists the project as **pre-release**, and production use requires a **compatible Linux kernel carrying Shirudo's patches plus TPM 2.0**, which is a substantial deployment bar. Cisco has a technical webinar scheduled for **December 15**.

### Yann LeCun accuses Dario Amodei of hyping danger to outlaw open models

The most-read AI item of the window was not a model. ### Virginia and Oregon sue Musk's companies over Grok's sexualized images

### Anthropic opens Enterprise Frontier Safeguards — and "zero retention" needs an asterisk

Anthropic began rolling out an early version of **Enterprise Frontier Safeguards (EFS)** for **Mythos and Fable** customers, reported **November 23–24**, with a public beta described as opening **November 23** ([Bloomberg](https://www.bloomberg.com/news/articles/2026-11-23/anthropic-rolls-out-zero-data-retention-policy-for-advanced-ai), [Business Standard](https://www.business-standard.com/technology/tech-news/anthropic-introduces-zero-data-retention-option-for-firms-using-advanced-ai-126112400117_1.html)). It partially reverses the policy introduced with Fable 5 / Mythos 5 in June, which required **30-day retention** and overrode existing zero-data-retention agreements.

**What actually changes is narrower than the headlines:** prompts and responses are **still retained for 30 days** — but in the **customer's own cloud account** rather than Anthropic's. Anthropic runs periodic checks for cyberattack indicators; on a hit, the customer is notified and Anthropic gets an alert but reportedly **cannot access the underlying data**. Enterprises must **apply**; it is not automatic, and the eligibility criteria are not clearly specified in any coverage. Sources conflict on whether Mythos is fully included or whether eligible customers get ZDR on Fable as a **bridge** until EFS is complete — verify terms directly with Anthropic. **Worth reading against yesterday's item** on the OpenRouter provider breaches, where ZDR flags were ignored in two incidents: moving the retention boundary to the customer's own cloud is a structural answer to exactly that failure, rather than another promise.

**1. [EL4CTEO/fast-anything](https://github.com/EL4CTEO/fast-anything)** — *profile the app, let an agent port only the slow functions to Rust, and verify the port against recorded real calls before switching it on.* **MIT**, **3.3k stars** (created after **Nov 14**, the steepest new-repo velocity on the board), **216 forks**, **9 open issues**, **9 open PRs**, **87 commits**, no releases yet. The pipeline is five commands: `scan` profiles and ranks functions by time spent and portability; `port` **records up to 500 real calls** and generates a one-function Rust crate plus a `TASK.md` for the agent; `verify` builds in release mode and replays those calls **plus derived edge cases** (NaN, infinities, −0.0, empty and very large inputs) and shrunk inputs; `enable`/`disable` inserts or removes a single marked block; `bench` and `report` compare the two. **A port is enabled only if every case matches** (floats within 1e-9, errors matching) **and it is not slower per call**, and `FAST_ANYTHING_DISABLE=1` falls back to the original.

**Why it's trending, and why it's better than it sounds:** the "rewrite it in Rust with an agent" genre has been producing repos all month (this is the third from the `*-anything` family, after **rust-anything** and **safe-anything**). What makes this one defensible is that **the verification gate is the product** — and the README's own worked example is a **failing** port (byte vs. character comparison) that missed **148 of 500 recorded calls** and was therefore rejected. Publishing your tool's own near-miss is the opposite of how this category usually markets itself. **Caveats:** self-reported speedups spanning **2.7×–116×** on fuzzy-dedupe-style workloads (Python 4.91s → 42ms is the 116×; the Java 3× is noted by the author as ~11× on the function with the rest being JVM startup), measured on an **i5-10500** or a 4-core GitHub Actions runner; only **top-level deterministic functions taking plain data** are eligible; each language needs its own runtime (Python 3.10+, Node 22+, Ruby 3.3+, Java 22+, Go 1.22+, PHP 8.1+ with FFI, R 4.0+, .NET 8+) plus a local Rust toolchain; **SYCL kernels are not ported**; and verification is **only as good as the recorded calls**, which is a real ceiling on the whole approach.

**2. [sybil-solutions/inference-optimisation-skill](https://github.com/sybil-solutions/inference-optimisation-skill)** — *an agent skill for making a local LLM server faster, with a measurement protocol strict enough to be worth copying.* **MIT**, **2.3k stars** (created after **Nov 14**), **214 forks**, **3 open issues**, **19 open PRs**, and — notably — **1 commit** on `main`. It covers single-user and concurrent decode, speculative decoding, prefill, KV-cache sizing, and startup/TTFT, under a memory cap, with results required to pass a **full-context stability check**. The six-step method is the interesting artifact: **compute the theoretical ceiling first**, change one thing at a time, **measure against interleaved controls**, log every result **including failures**, gate on long-context retrieval, and qualify a clean pinned build before publishing. Ships `SKILL.md`, a `references/` tree (ceilings, measurement pitfalls, levers, gotchas) loaded on demand, and a **stdlib-only Python + bash harness** (`bench.py`, `ceiling.py`, `queue.sh`, `mem.sh`) that benchmarks any OpenAI-compatible server.

**Why it's here:** nearly every agent skill on these trending lists automates *producing* something. This one automates **not fooling yourself** — it treats a single-run delta of **5–10% as noise**, demands interleaved controls, and requires failed approaches be recorded in `PLAN.md`. Among a month of skill bundles with no methodology at all, that is the differentiator. **Caveats:** every number is **self-reported on named hardware** and specific to model, quantization and engine — e.g. Intel Arc B390 iGPU single-user decode **43.6 → 53 tok/s**, 256K prefill **297 → 628 tok/s**, startup **113 → 43s**; 4× H200 NVL at **229.1 tok/s decode** after fixing a crash under load. The author also states where it **fell short**: decode on the B390 reached only **~55% of the estimated practical target**, attributed to GEMV kernel efficiency. **One commit means no visible development history**, and several model names cited (Qwen3.8, DeepSeek-V4.1) are not independently verified here.

**3. [pierridotite/mobile-agent-testers](https://github.com/pierridotite/mobile-agent-testers)** — *twenty Claude Code agents exploring your app on twenty emulated phones in parallel, on GitHub's free runners.* **MIT**, **1.5k stars** (created after **Nov 5**), **148 forks**, **63 commits**. Each agent plays a **persona** — "iPhone SE, Swedish, largest text size" — and either explores freely or works a briefed feature, then files a bug report **with screenshots**; no test scripts are written. Supports Flutter, React Native, Expo, native Kotlin and Swift, KMP, Capacitor and .NET MAUI, across modes for exploration, single-feature runs (deep links, app relaunch, ~30-action budget), **bug reproduction** (agents answer yes/no/unclear on each reported issue), improvement reports, and **version comparison** running identical personas against two branches.

**Why it's here:** the reported runs are specific enough to argue with, which is rare. **LocalSend: 20 phones, 46 distinct bugs, 69 minutes, $4.62. AnkiDroid: 10 Android phones, 43 distinct issues, under 10 minutes, $4.69.** A planted-bug control found **9 of 11** for **$0.87**. At roughly **$0.15–0.55 per phone** with free public-repo runners, that is a different cost structure from a QA contract, and the positioning is honest: complementary to Maestro or Appium, which run the tests *you* wrote, while these agents look for **"what nobody thought to test."** **Caveats, several load-bearing:** findings are "only as good as the model's reading of screenshots and its reasoning," especially on cheaper models (Haiku is supported); the README calls it **"a check before a real A/B test, not a replacement for one"**; **GitHub bills macOS minutes at 10× on private repos**, which undercuts the cost story for exactly the closed-source apps most likely to want this; and the hosted team version is only "exploring."

**4. [alexeyw/lot-map](https://github.com/alexeyw/lot-map)** — *a live transit-map of what your agent is doing, beside the chat.* **MIT**, **1.1k stars**, **120 forks**, **135 commits**. A Claude Code plugin that lights up stations (**You, Model, Memory, Files, Shell, Network, Browser, Agents, Skills, Hooks**) as tool calls, model steps, skills, subagents and compaction events fire. It **runs locally and sends nothing anywhere** — no network requests, no model calls, nothing added to the conversation. Renders three ways: text rows (default), a real image in kitty/Ghostty/iTerm2 3.7.8+, or **braille-dot text in any terminal**; plus eight languages, a context-window ring, and an optional per-call token-growth estimate.

**Why it's here:** agent observability has been an enterprise-dashboard category. This is the **single-developer, zero-telemetry** version of it, and the design is disciplined where it counts: **classification is by name only, never content** — a file shows its last two path segments, a web call shows the host without the path, a shell command shows the model's own short description rather than the command line. The README then does the thing almost no plugin README does: **it names the privacy hole in its own design** — the mod is handed each tool call's **full input** — and points you at the exact function (`classify` in `hooks/classify.ts`) and `PRIVACY.md` to check that claim yourself. **Caveats:** heuristic classification (a script that opens a connection shows as Shell; heredoc text is not read; lines over 8,000 characters never show as Files); `contextCost` figures are **estimates, shown one step late**, and absent for subagents; on **Team/Enterprise logins** the transcript may show skipped-hook notices, and disabling `guardedHooks` costs you the Hooks station; **iTerm2 3.7.7 leaks memory badly** on every image frame, so image mode is disabled there; needs a **144-column pane**; and only **Claude Code 2.1.321 on macOS** is stated as tested. A marketplace install **follows `main`**, so updates bring whatever is currently there — the README advises reading the diff first.

**Also worth a look:** **[agentes-chat/agentes-chat](https://github.com/agentes-chat/agentes-chat)** (**AGPL-3.0-only**, setup CLI MIT; **2.0k stars**, 394 forks, **11,252 commits**) — a self-hosted Slack alternative where **agents are channel members** with a role, an owner and a **monthly budget**, using Claude/OpenAI/Gemini models plus MCP tools, a browser, and scheduled or event-triggered routines, with **merges and deploys held for human approval in the chat**. Bun/Hono/Drizzle/Postgres server, React web, Expo phone, Tauri desktop. It arrives the same week as `itsaplan` (yesterday's issue-tracker-with-agents) — the same idea applied to the chat channel instead of the work item. **Caveats:** a long list of **Beta** components (agent browser, Postgres connector, mailboxes, phone, desktop, Docker-free hosting), unsigned Windows and un-notarized macOS builds during beta, each org supplying its own model keys, and **193 open issues against 322 open PRs** — a backlog worth weighing before self-hosting it.
